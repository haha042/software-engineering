# 数据保留与备份恢复

| 记录 | 最低保留期 | 当前处理 |
|---|---|---|
| 订单及关联快照、图片与事件 | 1 年 | 整体保留，等待订单终结和争议关联可可靠识别后再接入到期清理 |
| 举报和管理日志 | 1 年 | 保留现有管理日志，举报模型待实现 |
| 争议资料 | 处理结束后 1 年 | 保留已有历史，等待争议结束时间和证据引用可查询后再接入到期清理 |
| SQLite 日备份 | 最近 7 份 | 启动后立即检查，每分钟检查一次 UTC 日期。同一天只保留一份，成功生成后轮替 |

## 运行及恢复

启动业务系统后，备份保存在数据库旁的 `<数据库文件名>.backups` 目录。对默认数据库，目录为 `data/campus.sqlite.backups`。备份通过 SQLite 在线备份 API 创建，涵盖当时已经提交的数据。使用自定义数据库路径时，部署环境应为备份目录设置适当的文件访问权限。默认数据目录及其备份由 Git 忽略。

恢复时使用新路径，保留原库，以便独立核对。先确保目标父目录存在。以下命令可在业务系统目录的 macOS 终端或 Windows PowerShell 中运行。

```text
npm run restore -- data/campus.sqlite.backups/campus-2026-11-25.sqlite data/restored.sqlite
```

工具检查 SQLite 完整性和外键关联，且拒绝覆盖已有文件。恢复后在独立运行环境用 `DATABASE_PATH` 指向恢复副本，核对用户数、订单与商品关系、快照、确认和处置历史。

## 演示验证

在业务系统目录运行 `node --test test/backups.test.js`。macOS 上用虚构数据及模拟时钟推进九天，验证同日并发触发、轮替后保留七份、独立恢复和拒绝覆盖。测试模拟最新备份后 24 小时发生故障，恢复副本缺少预期的一条备份后写入。恢复计时包含完整性检查和复制，本轮完整回归中实测 1.78 毫秒，11 项测试全部通过。

持续停机或长期备份失败会使实际恢复点落后。模拟时钟与演示数据的结果适用于此次演练，实际部署仍需验证备份间隔、服务切换耗时和 Windows 环境。
