## 1. 为什么需要这份契约

需求侧对「版本」和「快照」有明确约束：

- **UC-11 买家下单**（需求 2.4）：获取方确认后，系统重新核验**权限、版本及状态**；同一次业务处理创建订单并**保存交易约定快照**；「**快照版本已改变时提示刷新后重新确认**」。
- **VT-06 本人下单与版本变化**：买家已看到 v1，商品变为 v2 后仍提交 v1 → **旧版本拒绝并要求重新核对，刷新后仅有效约定创建订单**。
- **VT-21 快照与认证历史**：商品恢复可编辑后修改标题/分类/图片 → **旧单仍显示原约定及旧图版本，不被当前商品覆盖**。
- **VT-24 伪装文件与历史图片授权**：**历史有权者仍可读取原图版本**；非法/无权限请求被拒绝。
- **QR-11**：订单快照不因商品编辑改变；**非参与者不能读订单图片**。
- **UC-12**：接受/取消/超时并发仅一个有效转换成功。

上述 VT-06/21/24 在需求基线中状态均为「未执行」。

## 2. 当前实现的事实核对（基线 ae4b2c64b303）

来源：本分支 `业务系统/src/products.js`、`src/orders.js`、`src/database.js`、`src/app.js`、`public/orders.js`、`test/product-edit.test.js` 实读。

| 观察点 | 当前实现 | 对契约的影响 |
|---|---|---|
| 商品版本字段 | `products` 表**无** `version` / `updated_at` / 内容版本列 | 详情无版本可返回，下单无版本可校验（#13 前置） |
| 商品编辑 | **已有** `PATCH /api/products/:id`（C04，PR #40）：驳回/在售可改，改完重新进入审核；审核中、预订中、已成交、草稿、已下架禁止修改 | 「商品编辑」不再是缺口；但编辑期间的版本语义未定义 |
| 编辑对图片的处理 | 编辑时 `DELETE FROM product_images WHERE product_id=?` 后重新插入**新图片行** | 旧图片 ID 会失效；已引用旧 ID 的历史订单可能读不到原图 |
| 订单快照 | `orders.snapshot = JSON.stringify(p)`，p 为 `SELECT * FROM products` 整行；**不含图片数据** | 无「订单创建时的目标图片」可固化（#14 缺口） |
| 现有「快照不变」保证 | `test/product-edit.test.js` 断言预订期间商品禁改、快照 title/price 保持 | 靠**状态锁定**实现，不是靠**版本校验**；商品恢复在售后改图不受此保护 |
| 详情与下单参数 | `GET /api/products/:id` 返回 `p.*` + `images`（`/api/images/:id` 列表），**无版本**；`POST /api/orders` 接收 `productId / requestKey / offer / topup / payer`，**不接收版本** | #13 前后端均需补字段 |
| 图片授权 | `GET /api/images/:id` 在 `status!=='live'` 且非 owner/admin/「该商品订单参与者」时返回 404；参与者按 `orders WHERE product_id=?` 判断 | 授权按**商品**维度而非**订单快照**维度；旧图版本无法单独授权 |
| 幂等请求键 | **已实现**：`requestKey` + `UNIQUE(buyer_id, request_key)`；同键不同参数返回 409「请求标识已用于不同参数」，同键同参数返回原订单 id | #17 后端基础已具备，前端失败重试是否保留标识待核对 |
| 错误响应 | 全局仅中文 `error` 文案，无稳定业务错误码 | 旧版本拒绝、参数复用拒绝需约定可判定的响应格式 |

**结论**：C04 合并后，「商品可编辑」已成立，反而使 #14 的风险具体化 —— 编辑会删除旧图片行，而订单快照不存图片；同时版本字段仍完全缺失，#13 无从落地。这正是 #12 需要先冻结契约的原因。

## 3. 待与商品维护负责人确认的五个问题

> 对应 Issue #12 验收条件第 1 条。**以下为待确认问题，不是已达成结论**；本 PR 不代替人工确认。

1. **版本何时变化**：首次审核通过算 v1 吗？C04 的「在售改动重新审核」通过后是否递增？驳回后重提是否递增？标题/分类/描述/价格/**图片**分别是否算版本变化？C05 下架重新上架、管理员改分类是否递增？版本字段与递增逻辑由哪个模块负责（涉及共享 `database.js`，须按 `CONTRIBUTING.md` 先约定字段与事务边界）。
2. **旧版本下单响应**：过期版本用哪个 HTTP 状态与错误码（候选 409 + 稳定业务码，**待确认**）？提示「刷新后重新确认」时 `requestKey` 保留还是重新生成（直接决定 #17 重试行为）？必须保证「订单与商品状态均不变」。
3. **旧订单兼容**：现存订单的 `snapshot` 无版本、无图片数据，是否回填？默认值与迁移脚本如何定？「已有订单按契约兼容」的判定标准与双平台验证方式是什么？
4. **图片访问范围**：订单图片是**复制到订单侧独立存储**（候选方向，待确认）还是**图片版本化 + 引用**？非参与者返回 404 还是 403？订单结束、`paused` 暂停、商品下架或删除后分别如何授权？「历史有权者仍可读取原图版本」（VT-24）如何界定有权者？
5. **所需验收样例**：VT-06（v1→v2 旧版本提交）、VT-21（改标题/分类/图片后查旧单）、VT-24（伪装 MIME、无权访问、有权者读原图）三条各自的最小数据集、执行平台（macOS / Windows 是否都要跑）与证据形式。

## 4. 拟定契约（未生效，仅供讨论）

> **未经第 3 节确认，不得作为 #13 / #14 / #17 的实现依据。**

- 字段：`products.version INTEGER NOT NULL DEFAULT 1`；`GET /api/products/:id` 增加 `version`；`POST /api/orders` 增加必填 `productVersion`。
- 校验：下单事务内重查 `SELECT * FROM products WHERE id=?`，要求 `status='live'` 且 `p.version === b.productVersion`；不匹配返回约定错误码并整体回滚（商品状态不变、不插入订单）。
- 快照：下单时把「商品字段 + 版本 + 目标图片数据」固化到订单侧；旧订单渲染只读快照，不再读取当前 `product_images`。
- 授权：订单图片按订单参与者鉴权（buyer_id / seller_id，管理员按需求 4.3 节），非参与者 404；已有订单按第 3 节第 3、4 项的确认结果兼容。
- 重试：沿用现有 `request_key`；响应不确定时前端保留原标识，同参数返回原订单，改参数 409。
- 顺序：#12 确认 → #13 版本校验 → #14 图片固化 → #17 重试。
